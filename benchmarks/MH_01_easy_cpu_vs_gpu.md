# VINS-Fusion Adapter — CPU vs GPU benchmark on EuRoC MH_01_easy

_Recorded 2026-09-23. Machine-generated results: `benchmarks/MH_01_easy_cpu_vs_gpu.json`._

## Headline result

| variant | binary | median wall | throughput | TUM rows |
| --- | --- | --- | --- | --- |
| CPU | `vins_adapter` | **468.73 s** | 7.86 frames/s | 3672 |
| GPU | `vins_adapter_gpu` | **245.12 s** | 15.02 frames/s | 3672 |

- **Speedup (median): 1.91x**, wall-time reduction **47.7 %**.
- Trajectory cross-check: **3672/3672 poses matched**, translation RMSE **29.6 mm**
  (max 81.5 mm), max rotation difference **0.72°** — small and expected, since
  the GPU tracker runs in float on the device and the CPU path on the host.

## Benchmark settings

**Dataset / episode**
- EuRoC MAV `MH_01_easy` (Burri et al., IJRR 2016): stereo global-shutter
  grayscale, 752×480, 200 Hz IMU. 3682 frames (cam0 == cam1), ~363 s of motion.
- Staged on local disk at `/data/home/xiamingchen/datasets/euroc/MH_01_easy`
  (2.6 GB). The source copy on COS (`cos-jamintest-sh-1305424723`) is a
  `fuse.cosfs` mount where listing/reading the frame dirs takes minutes, which
  would dominate and destabilize wall-clock timing — so it was copied to local
  ext4 first.
- Adapter config (`.../MH_01_easy/config.yaml`, generated by
  `benchmarks/prepare_euroc.py`): `imu: 1`, `num_of_cam: 2`,
  `estimate_extrinsic: 2`, `max_features: 200`, EuRoC cam0 pinhole + radtan
  intrinsics, `T_cam0_body`/`T_cam1_body` from each `sensor.yaml`, per-frame
  timestamps from `frame_times.csv`, IMU from `imu_seconds.csv`.

**Builds**

  `linux/amd64`, `gpu: true`.

**Host / runtime**
- CPU: Intel Xeon Platinum 8255C @ 2.50 GHz, 16 vCPU, 62 GB RAM.
- GPU: NVIDIA Tesla T4, 15 GB, driver 550.90.07, CUDA toolkit 12.4.
- Node: `VM-64-201-tencentos`, Linux 6.6.30 (TencentOS 4.2), x86_64.
- Both binaries single-threaded (`MULTIPLE_THREAD=0`), one process per run.

**Method** (`benchmarks/benchmark_cpu_gpu.py`)
- 1 untimed warmup + 3 timed runs per variant, wall-clock around the whole
  process (frame decode + tracker + estimator + TUM write).
- Each binary is invoked directly (not through the launcher); the GPU run gets
  `VINS_OPENCV_CUDA_DIR=<CUDA OpenCV install>` so the CUDA/OpenCV closure
  resolves. CPU uses the bundle's own conda OpenCV via `$ORIGIN/lib`.
- Exact command:

```bash
VINS_OPENCV_CUDA_DIR=/data/home/xiamingchen/opencv-cuda-4.13.0/install \
python3 benchmarks/benchmark_cpu_gpu.py \
  --config /data/home/xiamingchen/datasets/euroc/MH_01_easy/config.yaml \
  --runs 3 --warmup 1 --require-gpu \
  --json benchmarks/MH_01_easy_cpu_vs_gpu.json
```

## Notes and caveats

- The speedup is bounded by work that stays on the CPU: PNG decode, the
  sliding-window optimizer (Ceres), and the estimator front-end. Only the
  feature tracker (corner detection + optical flow) moves to the GPU, so ~1.9x
  is the expected ceiling for this workload, not a GPU-utilization figure.
- The GPU wall time is remarkably stable (±0.5 s across runs); the CPU spread is
  wider (±7 s), consistent with host scheduling on a shared 16-vCPU VM.
- Data is read from local disk and page cache is warmed by the warmup pass;
  timings are I/O-inclusive.
- GPU vs CPU trajectories are intentionally not bit-identical (float on device
  vs host); the 29.6 mm translation RMSE is small relative to the ~45 m path.

## Latent bugs that had to be fixed for the GPU path to work

None of these had ever been exercised because the GPU build had never run:

1. `benchmarks/prepare_euroc.py` wrote the 4×4 `T_BS` as **four** rows; the
   adapter's `read_cam_transform` accepts exactly **three** (`src/adapter_spec.h:97`,
   locked by the unit tests) → every generated EuRoC config was rejected.
2. `Dockerfile` GPU link flags comma-joined two `-Wl,-rpath-link` dirs, so `ld`
   treated the second as an input file (`cannot find /opt/ros1/lib`).
3. `Dockerfile` GPU build: the CUDA fork's `vins_estimator/package.xml` lacks the
   `camera_models` dependency the CPU fork declares, so `catkin build vins`
   configured `vins` before `camera_models` existed.
4. `Dockerfile` GPU build: the CUDA OpenCV's `OpenCVConfig.cmake` hard-requires a
   build-time CUDA toolkit; the build image has none (CUDA is worker-provided).
   Patched in-image to stub that requirement.
5. CUDA OpenCV `BUILD_LIST` omitted `cudafilters`; without it
   `HAVE_OPENCV_CUDAFILTERS` is undefined and `cudaimgproc`/`cudaoptflow` compile
   to `throw_no_cuda` stubs — the GPU tracker then aborts at run time. Adding it
   makes `createGoodFeaturesToTrackDetector` and `SparsePyrLKOpticalFlow::create`
   real.
